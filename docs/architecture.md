# 目标架构

## 总体形态

**模块化单体（Modular Monolith）**：一个可运行的 Go 服务，内部按业务域拆包，每个域自治；未来需要时可把某个域独立部署。

## 架构图

```
┌──────────────────────────────────────────────┐
│ cmd/server（组合根：唯一装配点）                │
├──────────────────────────────────────────────┤
│ internal/tasks                               │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐  │
│  │   api    │ → │   app    │ → │  domain  │  │
│  │ HTTP 适配 │   │ 用例编排  │   │ 模型+端口 │  │
│  └──────────┘   └──────────┘   └──────────┘  │
│                                 ↑            │
│                        ┌────────┴─────────┐  │
│                        │ infra（适配器实现） │  │
│                        │  memory / mysql  │  │
│                        └──────────────────┘  │
└──────────────────────────────────────────────┘
```

## 依赖规则

1. **依赖只能从外向内**：`api → app → domain ← infra`
2. **domain 不 import 任何框架/基础设施**：只定义实体、规则、端口（接口）
3. **infra 实现 domain 的接口**：替换数据库/搜索/消息只需新增适配器
4. **组合根唯一装配**：所有依赖在 `cmd/server` 显式创建并注入

## 为什么这样设计

| 决策 | 依据 | 好处 |
|------|------|------|
| 模块化单体 | 避免过早微服务，同时获得模块边界 | 部署简单 + 可演进 |
| 按域分包 | 限界上下文 | 各域独立演进，不互相污染 |
| domain 最内 | 整洁架构依赖规则 | 业务规则可单测、可替换 |
| 端口在 domain | Hexagonal Ports & Adapters | 换存储/框架不动业务 |
| 组合根唯一 | Dependency Injection | 依赖显式可见，无全局单例 |
